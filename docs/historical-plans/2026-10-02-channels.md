# Plan: Channels — a user-curated, draggable list of feed sources

## Context

Right now the feed's source is picked from a dropdown (`SettingsTab/index.tsx` ~L378) that lists **every** saved scene and marker filter in Stash. The choice is stored as `currentFilterId`, and there is one global `isRandomised` switch. That has two problems:

- **Too rigid.** A feed source has to already exist as a Stash saved filter.
- **Too noisy.** Users with lots of filters have to scroll through ones they never use in Stash TV.

The plan replaces the dropdown with a short, ordered list that the user curates. Each entry wraps one filter, and each filter (source) carries its own "randomise" setting. Selecting an entry switches the feed to it. A dropdown under the list picks what loads at startup: the last viewed entry, or the first one in the list.

The stored shape has to leave room for two later features: several filters per entry, and custom filters that don't live in Stash.

## Naming: "Channels" (recommended)

This is a TV app and users switch between these entries, so "channel" is the natural word.

- It works for future entries that mix several filters, or use filters that aren't Stash filters. A channel is defined by its **sources**, not by being a filter.
- It also avoids a clash: "filter" already means two things in `useMediaItemFilters.ts` (saved vs searchable), and "playlist" suggests a fixed, ordered list of scenes, which these aren't.

Other names considered:

| Name | Problem |
|---|---|
| Feeds | Clashes with `FeedPage` and `useFeedStore` |
| Playlists | Suggests fixed scene lists |
| Stations | Fine, but radio-flavoured |
| Sources | Better kept as the word for the parts that make up a channel |
| Collections | Clashes with Stash "groups" |

Terms used in code:

- `Channel` / `ChannelConfig`: one entry in the list.
- `ChannelSource`: one thing that supplies media to a channel.
- "Active channel": the channel the feed is currently showing.

## Storage design (`src/store/tvConfig.ts`)

New file `src/components/channels/channel-config.ts`, with yup schemas following `action-button-config.ts`:

```ts
// A source is a tagged union so new kinds are additive, not a migration.
type SharedSourceFields = { randomise: boolean }  // per source: moved here from the global isRandomised
type StashSavedFilterSource = SharedSourceFields & { type: "stash-saved-filter"; savedFilterId: string }
// future: { type: "custom-filter"; mode: FilterMode; find_filter; object_filter }  (SavedFilter-shaped)
// "Everything of one entity type": the existing empty-filter logic in useMediaItemFilters, as a source
type AllMediaSource = SharedSourceFields & { type: "all"; entityType: "scene" | "marker" }
type ChannelSource = StashSavedFilterSource | AllMediaSource

type ChannelConfig = {
  id: string                 // stable generated id; never derived from the filter id (the same filter can be in 2 channels)
  sources: ChannelSource[]   // v1: exactly one (yup .min(1).max(1)); an array now so multi-source needs no migration
}
```

New `TvConfig` keys:

- `channels: ChannelConfig[]`, default `[]`.
- `startupChannel: "last-viewed" | "first"`, default `"last-viewed"`.
- `lastViewedChannelId?: string`. This replaces `currentFilterId` and stays in Stash config, the same backend as today, so the behaviour of syncing across devices doesn't change.

Remove `currentFilterId` and `isRandomised`.

**Store references, not copies:**

- Don't store the filter's name or entity type. Read both live from Stash via `availableSavedFilters`, so renaming a filter in Stash shows up straight away.
- If a referenced filter has been deleted, show the entry as "Missing filter" with its edit and delete buttons; don't drop it silently.
- An optional `name` override joins the schema later, when multi-source channels need one. Adding it doesn't need a migration.

**What the future features fit into:**

- **Multi-source.** `randomise` belongs to each source: it controls the order of that source's own media, so in a mixed channel one filter can be shuffled while another keeps its sort. How sources are combined (interleaving, for example) is a separate, channel-level policy, added when multi-source arrives.
- **`randomise` lives in the shared source fields**, so every source kind, including custom filters, gets it. Each source gets its own random seed.
- **"All" source.** `resolveChannelSource({type: "all", entityType})` returns the empty SavedFilter that `useMediaItemFilters.ts` (L138-146) builds today: `{id: "", mode, name: "", filter: ""}`, with `mode` taken from `entityType`. That inline object is pulled out into a shared `makeEmptySavedFilter(mode)` helper, which both the resolver and the no-channels fallback use. "All markers" comes free from the same code (`mode: SceneMarkers`). An "all" source can never go missing.
- **Custom filters.** A future `custom-filter` source stores a SavedFilter-shaped object inline. A single `resolveChannelSource(source) → SavedFilter`, which can be async, means `convertSavedToSearchableFilter` works for every kind of source unchanged.

**Migration** (bump the persist `version` 2 → 3, in the existing `migrate`):

- If `currentFilterId` is set:
  - create `channels: [{ id, sources: [{type: "stash-saved-filter", savedFilterId: currentFilterId, randomise: !!isRandomised}] }]`
  - set `lastViewedChannelId` to that channel's id
- Delete `currentFilterId` and `isRandomised`.
- Add a test case to `test/unit/store/tvConfig-migration.test.ts`.

## Feed behaviour (`src/hooks/useMediaItemFilters.ts`)

- Add `activeChannelId` to `useGlobalFilterState`. It is **transient**. The persisted `lastViewedChannelId` is written every time the user switches channel, but startup mode `"first"` doesn't overwrite it.
- **Choosing the startup channel** replaces the `currentFilterId` branch in the initial-load effect:
  - `"first"` → `channels[0]`
  - `"last-viewed"` → `lastViewedChannelId` if it's still in the list, otherwise `channels[0]`
  - no channels → the existing fallback: Stash's default scene filter, then the empty "All scenes" filter. `channels` still defaults to `[]`, so new users keep Stash's default filter.
- **Switching channel.** Add `setActiveChannel(id)` to the hook's return value. It sets `activeChannelId` and `lastViewedChannelId`, then loads `sources[0]` through the existing `setCurrentMediaItemFilterById`.
- **Randomise.** `isRandomised` is replaced by the `randomise` of the source being loaded (`sources[0]` for now). `convertSavedToSearchableFilter` takes it as a parameter instead of reading global config, so it can be applied per source later. The random seed is already regenerated whenever a filter loads.
- **Editing the active channel** (new filter or new randomise setting) reloads the feed. This works through the effect dependencies, keyed on the resolved saved-filter id and that source's `randomise`.
- `isCurrentFilter` becomes "belongs to the active channel". Expose `activeChannel` from the hook as well.
